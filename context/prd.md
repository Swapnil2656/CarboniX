# Product Requirements Document (PRD): Carbonix

> [!IMPORTANT]
> **Hackathon Objective & Context**
> We are building Carbonix for an Expo-track hackathon. The product must be a mobile-first developer tool that delivers real value. The project MUST feel like a production-grade developer platform, not a student CRUD application wearing a sustainability costume. Carbonix wins because it exposes infrastructure emissions as programmable data.

## 1. The Problem

Every time you deploy code to the cloud, servers somewhere in the world consume electricity. That electricity is generated by power plants — coal, gas, nuclear, solar, hydro — and each has a different carbon cost. The problem is simple and brutal:

**Developers know their AWS bill to the dollar. They have zero idea what their carbon bill is.**

The global ICT sector accounts for 2–3% of global CO₂ emissions — comparable to the entire aviation industry. Data centers are a major chunk of that. Yet there is no mainstream developer tool that answers "how much CO₂ does my infrastructure emit?" Cloud providers bury carbon data in annual PDF sustainability reports. It's not queryable. It's not in any dev workflow. Nobody checks it — not because they don't care, but because there's no easy tool to do it.

**Carbonix is that tool.**

## 2. What Carbonix Actually Is

Carbonix is Postman for sustainability APIs — a mobile-first developer tool that tells you the carbon cost of your cloud infrastructure and exposes it as an open API any developer can build on. It is three things stacked on top of each other:

1. **Layer 1 — The API (backend)**. A Node.js + Express server with real endpoints. You POST your infrastructure config and it returns CO₂ data. Endpoints: `/calculate`, `/compare`, `/recommend`, `/history`, `/docs`. This runs on Railway or Render, always live.
2. **Layer 2 — The SDK (npm package)**. A JavaScript/TypeScript package that wraps the API. Developers can `npm install carbonix`, call `calculateCarbon()`, and get a CO₂ number in 5 lines without knowing anything about the actual carbon math underneath. This is what proves Theme 10.
3. **Layer 3 — The Expo app (showcase)**. A mobile-first developer console — like Postman but built in Expo React Native. You build API requests inside the app, fire them at the API, and visualize the results with charts. This is what judges see and interact with on demo day.

> **Key mental model**: The Expo app is not the underlying product. It's the SDK's live demo environment. The product is the API + SDK. The app proves it works.

## 3. SDK Explained From Zero

SDK stands for Software Development Kit. It's a pre-built package published so developers don't have to build the same thing from scratch. You use SDKs every single day (`npm install axios`, `import Stripe from 'stripe'`).

Without Carbonix, developers must: find the Cloud Carbon Footprint dataset, understand the formula, find grid intensity data per region, write the calculation logic, handle edge cases, outline an API, and deploy it. Weeks of work.

With Carbonix, it's 5 lines:
```typescript
import { Carbonix } from 'carbonix'

const sdk = new Carbonix({ apiKey: 'your-key' })

const result = await sdk.calculateCarbon({
  provider: 'aws',
  region: 'us-east-1',
  instanceType: 't3.medium',
  count: 4,
  hoursPerMonth: 720
})

console.log(result.co2_kg_month)   // → 28.2
console.log(result.rating)         // → "high"
console.log(result.recommendation) // → "Switch to eu-north-1 to reduce by ~98%"
```
The SDK returns a structured object with emissions, ratings, a breakdown by compute/memory/storage, and an actionable recommendation.

## 4. How It Actually Works (The Carbon Math)

**The full flow:** developer enters config in Expo app → app calls `POST /calculate` → API runs the carbon formula using Cloud Carbon Footprint data + grid intensity → returns CO₂ result → Expo app renders the chart and recommendation.

**The actual formula:**
```text
energy_kwh = (cpu_tdp_watts × cpu_utilization × hours × instances) / 1000
           + (ram_gb × 0.000392 × hours × instances)
           + (storage_gb × 0.0000002 × hours × instances)

co2_grams = energy_kwh × grid_intensity_gCO2_per_kWh
```

**Grid Intensity Examples:**
- `us-east-1` (Virginia) → 415 gCO₂/kWh (coal-heavy US grid)
- `eu-west-1` (Ireland) → 316 gCO₂/kWh (renewables mix)
- `eu-north-1` (Stockholm) → 8 gCO₂/kWh (near 100% hydro)

This means the same 4 servers running the same workload produce **50× more carbon** in Virginia than in Stockholm. That's not an estimate — it's real grid data. 

**Live Simulator Example (4x t3.medium on AWS us-east-1, 40% CPU, 720h):**
```text
CPU TDP for t3.medium = 55W
Compute energy = (55 × 0.40 × 720 × 4) / 1000 = 63.4 kWh
Memory energy  = (4 GB × 0.000392 × 720 × 4)  =  4.5 kWh
Total = ~67.9 kWh/month
CO₂ = 67.9 × 415 gCO₂/kWh = 28,179 g CO₂ = 28.2 kg CO₂/month
```
Switch to Stockholm (8 gCO₂/kWh) = **0.54 kg CO₂/month.**

**Data sources:** 
- Cloud Carbon Footprint dataset (github.com/cloud-carbon-footprint)
- Electricity Maps API

## 5. Theme Alignment & Hackathon Constraints

*   **Theme 02 — Climate & Sustainability**: The entire product domain is cloud carbon emissions. Every feature directly measures or reduces environmental impact (`/recommend`).
*   **Theme 06 — Infrastructure & Smart Systems**: Cloud infrastructure is the system being monitored. `/compare` and `/history` provide real-time infrastructure intelligence.
*   **Theme 10 — Developer Tools & Software Infrastructure (Core Identity)**: An API that developers build on top of is pure software infrastructure.
*   **Expo Track Mandatory Requirements**: Must feature Expo-native workflows, EAS Build/Update, API console optimized for mobile, and touch interactions.

## 6. Technology Stack Requirements

**Frontend (Expo Mobile App)**
- Framework: Expo SDK, React Native, TypeScript, Expo Router
- Mandatory Features: EAS Build, EAS Workflows, Expo Notifications, Expo Secure Store, Expo File System, Expo Constants, Expo Linking, Expo Splash Screen, Expo Updates, Expo Reanimated, Expo Gesture Handler
- Visualization: Victory Native or React Native Chart Kit
- State/Networking: Zustand/Redux Toolkit, React Query, Axios

**Backend API**
- Runtime: Node.js, Express.js, TypeScript
- Features: REST API, OpenAPI/Swagger, Rate limiting, Calculation and Recommendation Engine
- Database: PostgreSQL (preferred) or MongoDB
- Deployment: Railway or Render

**SDK Package**
- Package: `carbonix` (TypeScript-first)
- Distribution: npm package
- Goals: Stripe/Supabase level usability. Minimal setup, strong typing support, Promise-based API.

## 7. Website & Documentation Portal Requirements

Carbonix requires a complete developer-facing website for credibility.
- **Landing Page**: Embedded live calculator. Hero: *"Measure the carbon footprint of your cloud infrastructure in real time."*
- **Documentation Area**: Install (`npm install carbonix`), Auth, Quick Start, API Reference, Region Comparisons, Methodology, CI/CD Integration.
- **Interactive Playground**: Postman-style request builder in the browser.
- **Dashboard**: API usage tracking, analytics, region suggestions.

## 8. Mobile Application Vision (Core Screens)

A touch-optimized developer console. NOT a generic web wrapper. Mobile-first infrastructure monitoring.
1. **Authentication**: Sign up, login, secure JWT via Secure Store.
2. **API Console (Main Demo Screen)**: Build requests visually (provider, region, instances, utilization). View raw JSON responses. Touch-optimized.
3. **Carbon Visualization**: Interactive charts of emissions and configurations.
4. **Recommendation Engine**: *"Move from us-east-1 to eu-north-1 to reduce emissions by 98%."*
5. **History Screen**: Timeline analytics of past calculations.
6. **Notifications**: Push alerts ("Your AWS deployment emitted 18% more CO₂ this week").

## 9. API Architecture (Core Endpoints)
- `POST /calculate`: Calculate emissions for an architecture config.
- `POST /compare`: Compare multiple regions simultaneously.
- `POST /recommend`: Output greener deployment templates.
- `GET /history`: View calculation records.
- `GET /docs`: OpenAPI UI.
